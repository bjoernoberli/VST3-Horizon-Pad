# DSP invariant audit — 2026-09-20

Audit of Horizon Pad's DSP against the 20 rules in `.claude/rules/dsp-invariants.md`.
Methodology follows `dsp-sound-design-playbook.md` Part 8.4 (shimmer/feedback decay-slope
test) and Part 13 (G3 measure-in-the-fast-loop workflow), using `HorizonPadSoundTool`
(built from this branch) plus a Python/numpy/scipy analysis harness for octave-band
decay fitting. All renders below are reproducible with the flags shown; JSON/WAV
scratch output lived in the session's scratchpad, not committed.

**Scope note:** during this audit, `Source/dsp/FxChain.cpp`/`.h` were found already
modified on disk (uncommitted, unstaged) with a REVERB equal-power crossfade someone
had already implemented, apparently in response to a question earlier in this session
about REVERB making the pad louder. That existing work is what's audited and verified
below under #8, not replaced.

## #1 — No allocation/locking/I-O in `processBlock`

**Pass.** `HorizonPadAudioProcessor::processBlock` ([PluginProcessor.cpp:659](../Source/PluginProcessor.cpp)) only
touches pre-sized members: `layerBuffer`, `layerGain`, the four `LayerBase`
subclasses' `scratch`/`voiceState` arrays (fixed-size `std::array`, `kMaxVoices=8`),
and `FxChain`'s `dryMono`/`wetStereo` buffers, all sized once in `prepare()`/`prepareLayer()`.
The two `std::vector` members that exist in the audio path
(`AnalogEnsembleLayer::VoiceState::delayBuffer`, `OctaveShimmer::buffer`) are sized via
`.assign()` in `prepareLayer()`/`prepare()` only, never touched with `push_back`/`resize`
inside `renderVoice`/`processSample`. No `new`, no mutex, no file/console I/O anywhere in
the render path.

## #2 — `ScopedNoDenormals`

**Pass.** [PluginProcessor.cpp:661](../Source/PluginProcessor.cpp), first line of `processBlock`.

## #3 — Parameter smoothing / discrete-switch crossfades

**Pass** for all 12 host parameters — see #18's table (VOLUME 30ms, WIDTH 50ms, FILTER
20ms, REVERB 50ms, all per-sample; ATTACK/RELEASE only set ADSR shape at `noteOn`, so
block-rate application doesn't discontinuities in running audio). Preset recalls and A/B
buffer switches ([PluginProcessor.cpp:299-324](../Source/PluginProcessor.cpp),
[:363-400](../Source/PluginProcessor.cpp)) go through `setValueNotifyingHost` →
`parameterChanged` → the same smoothed targets, so an instant preset jump still ramps
over the existing 20-50ms windows, comfortably inside the 10-20ms rule.

**Related finding, not one of the 20, not fixed:** voice stealing kills the stolen voice's
envelope with `juce::ADSR::reset()` ([LayerBase.h:211-216](../Source/dsp/LayerBase.h),
called from [PluginProcessor.cpp:562](../Source/PluginProcessor.cpp) and
[:597](../Source/PluginProcessor.cpp)), which snaps envelope level to 0 with no fade. If
`findFreeVoiceSlot()`'s tier 2/3 steals a voice that's still at meaningful amplitude
(long-sustained pad, `kMaxVoices=8`, all four layers sharing the slot pool), that's a hard
sample-domain discontinuity — the DSP equivalent of a discrete switch with no crossfade.
I could not force this in `HorizonPadSoundTool` to get a `clickCount` reading: the CLI
only supports one simultaneous note-on/note-off group per render, not staggered timing,
so I can't script "hold 8 notes, let them settle, then trigger a 9th" in one render. Flagging
by code reading only — plausible real-world trigger (sustain-pedal-style ambient chord
work with >8 overlapping held notes), moderate severity, not fixed here since a fade-out
needs a real design decision (how long, per-voice ramp state) plus a listening pass.

## #4 — Nonlinearity oversampled/ADAA'd/documented

**Pass.** The only nonlinearity in the signal path is the output-stage `tanh` soft clip
([PluginProcessor.cpp:725-733](../Source/PluginProcessor.cpp)), run at the native rate,
not oversampled or ADAA'd. It's documented at the call site as a safety net for
pathological automation, not part of the normal sound, with a fixed 0.75 headroom trim
keeping normal signals in tanh's near-linear region — i.e. it's the "documented as
deliberately [rarely] aliasing" case the rule allows, though the comment doesn't use that
exact framing. Oscillators use polyBLEP-corrected saw (`polyBlepSaw`,
[LayerBase.h:354-370](../Source/dsp/LayerBase.h)); the naive triangle
(`triangleWave`, [LayerBase.h:375-378](../Source/dsp/LayerBase.h)) is documented as
low-alias-risk by design, which is an established, reasonable call for a triangle's weak
harmonic content.

## #8 — Wet/dry equal-power, character controls level-compensated

### REVERB — pass, verified, with an important methodology correction

`FxChain::process()` ([FxChain.cpp:83-100](../Source/dsp/FxChain.cpp)) mixes dry and wet
with an equal-power `cos`/`sin` crossfade, with the wet path pre-scaled by
`kWetCalibrationGain` ([FxChain.h:71](../Source/dsp/FxChain.h)) so the crossfade's
constant-power property isn't swamped by the reverb's own extra gain.

**This audit's first pass got this wrong.** A single-sample sweep of REVERB 0→1 on the
full 4-layer default mix (`--notes=60,64,67`, no solo) showed RMS climbing from ~0.021 to
~0.052 (+7.6 dB) — I initially treated this as a real gap in the already-existing fix and
lowered `kWetCalibrationGain` from 0.48 to 0.2 to compensate. A controlled follow-up
(N=5 renders per point, solo'd single layer to reduce oscillator-beat variance) showed
that was wrong: G=0.2 *undershoots*, producing a real ~8dB *drop* at REVERB=100%
instead of flatness, while the original G=0.48 is close to flat:

```
solo=root, 60/64/67 chord, N=5 renders per point, G=0.48:
  reverb=0.0   mean=0.02628
  reverb=0.5   mean=0.02438
  reverb=1.0   mean=0.02556      (max deviation ~0.5 dB, within run noise)

full 4-layer mix (no solo), N=5 renders per point, G=0.48:
  reverb=0.0   mean=0.02181
  reverb=0.28  mean=0.02166  (product default)
  reverb=0.5   mean=0.01901
  reverb=1.0   mean=0.01956      (max deviation ~1.2 dB, within run noise)
```

Root cause of the false alarm: with all four layers summed, up to ~10 detuned/drifting
oscillators per note beat against each other on multi-second cycles (`kOscDriftRateHz`
values of 0.08-0.37 Hz across the four layers, plus slower LFOs like
`WarmFoundationLayer`'s 0.13Hz "breathe"). A single 10s render's RMS depends on where in
those slow cycles it happens to land — run-to-run swings of 2-3x on the *same* setting are
possible on the full mix, which single-sample or 3-sample sweeps can't distinguish from a
real effect. `HorizonPadSoundTool`'s own header comment claims RMS is "stable run-to-run
to a small fraction of a percent" — that held for solo'd/simple renders in this audit but
not for un-solo'd full-mix chords; worth a note if that comment is revisited.

**Fix applied:** restored `kWetCalibrationGain` to 0.48 (its original, correct value) and
rewrote the constant's doc comment to record the 2026-09-20 re-verification and warn
against re-tuning it from a low-N full-mix measurement. See "Fixes applied" below for the
full before/after.

### WIDTH — minor, real, confirmed gap (not fixed)

```
solo=root, 60/64/67 chord, reverb=0, N=5 renders per point:
  width=0.0    mean=0.03716
  width=0.25   mean=0.03647
  width=0.5    mean=0.03434
  width=0.75   mean=0.03182
  width=1.0    mean=0.02951     (stdev 3.4-5.6% per point; the trend is well outside noise)
```

A real, monotonic ~20% (~2 dB) RMS *decrease* from WIDTH=0 to WIDTH=100%, confirmed with
5 reps/point (stdev 3-6% per point vs. a 20% trend). This exceeds the playbook's ~0.5-1dB
level-JND, so it's a genuine, audible, uncompensated level dip — a real #8 gap, though far
smaller than the REVERB scare above. Likely cause: `LayerBase::render()`'s per-layer
WIDTH mechanism ([LayerBase.h:280-299](../Source/dsp/LayerBase.h)) is a delay tap on one
channel with a `blendBack` mono-safety mix — not something built or tuned to be
power-flat, just to avoid the true-null mono-cancellation bug fixed in a recent commit.
**Not fixed here**: doing so means changing the delay/blendBack formula in `LayerBase.h`,
which affects the stereo-image character the mono-safety fix was specifically tuned for
(commit "Fix severe mono-cancellation bug in per-layer WIDTH (Haas) processing" — see
`git log`), and deserves a listening pass, not just a numeric patch. Flagging with numbers
for a follow-up.

## #10 — Modulated delays: Lagrange/Hermite, not linear/allpass

**Gap, confirmed, not fixed.** Two modulated delay reads both use plain 2-point linear
interpolation:

- `AnalogEnsembleLayer`'s flanger delay read
  ([AnalogEnsembleLayer.cpp:96-104](../Source/dsp/AnalogEnsembleLayer.cpp)) — delay time
  is continuously swept 2-11ms at 0.11Hz
  ([AnalogEnsembleLayer.cpp:91-92](../Source/dsp/AnalogEnsembleLayer.cpp)), read back with
  `readPos0`/`readPos1` linear-blend, no cubic/Hermite correction.
- `OctaveShimmer`'s grain read pointer
  ([OctaveShimmer.h:49-57](../Source/dsp/OctaveShimmer.h)) — reads at 2x speed
  (`ratio=2.0`, a fixed +1-octave shift, so the fractional read position moves twice as
  fast per sample as a real-time delay would), also linear-blended (`i0`/`i1`).

Both are textbook cases the rule calls out explicitly (modulated delay ⇒ Lagrange/Hermite;
linear/allpass is for static tuning only). Linear interpolation acts as a mild lowpass
that's harsher the faster the read position moves, so `OctaveShimmer`'s 2x-speed read is
the more affected of the two.

**Not fixed in this audit.** Swapping interpolators changes the flanger's/shimmer's actual
frequency response — an audible character change, not a pure bug fix — and both files are
normally in-scope for the `sound-designer` subagent's careful render-measure-listen loop
(per `CLAUDE.md`), not a blind numerical patch from an invariant audit. Recommend a
follow-up pass with that agent (or explicit sign-off to do it inline) rather than editing
it here without a before/after listening check.

## #16 — Feedback-loop filter peak magnitude <=1

**N/A**, confirmed by tracing every signal path in `Source/dsp/`: there is no custom
feedback loop anywhere in this project's own code. `AnalogEnsembleLayer`'s flanger is
feed-forward, not feedback — the delay buffer is written only with the dry oscillator
`stack` ([AnalogEnsembleLayer.cpp:89](../Source/dsp/AnalogEnsembleLayer.cpp)), never with
the combined `ensemble` output, so nothing recirculates.
`AiryChoirLayer`'s shimmer is a parallel send (highpass → pitch-shift → small reverb →
summed into output), not a loop — see #19 for the full trace and the empirical
confirmation. The only recirculating structure in the whole plugin is inside JUCE's own
`dsp::Reverb` (used for both the shared `FxChain` send and `AiryChoirLayer`'s own shimmer
reverb), a fixed-parameter, vendor-verified black box with no user-exposed feedback gain.

## #18 — Control signals to sample rate or <=32-sample sub-blocks

**Pass** for the 12 host parameters, **one real bug found and fixed** for
pitch-bend/mod-wheel.

| Control | Mechanism | Granularity |
|---|---|---|
| VOLUME (Ă—4) | `layerGain[i]` `SmoothedValue`, target set once/block, `getNextValue()` per sample ([PluginProcessor.cpp:671](../Source/PluginProcessor.cpp), [:648-655](../Source/PluginProcessor.cpp)) | per-sample, 30ms ramp |
| FILTER (brightness) | `smoothedBrightness`, ramped into `brightnessBlock` per sample ([LayerBase.h:106-109](../Source/dsp/LayerBase.h), [:234-239](../Source/dsp/LayerBase.h)) | per-sample, 20ms ramp |
| WIDTH (Ă—4) | `smoothedWidthSamples`, `getNextValue()` per sample inside the delay-tap loop ([LayerBase.h:288-298](../Source/dsp/LayerBase.h)) | per-sample, 50ms ramp |
| REVERB | `smoothedReverbSend`, `getNextValue()` per sample ([FxChain.cpp:85](../Source/dsp/FxChain.cpp)) | per-sample, 50ms ramp |
| ATTACK/RELEASE | Sets `juce::ADSR::Parameters` only at `noteOn()` ([LayerBase.h:193-200](../Source/dsp/LayerBase.h)) | not continuously modulating audio — a block-rate value here can't zipper since it only shapes a freshly-triggered envelope, not a live one |

**Bug found:** pitch-bend and mod-wheel (`PerformanceState`) were read once at the top of
`processBlock`, before the MIDI-event loop, and pushed into the layers once
(`layer->setPerformance(pitchBend, modAmount)`). Inside the loop,
`handleMidiMessage()` updates `performanceState`'s atomics for pitch-wheel/CC1 messages,
but nothing re-pushed the new value into the layers before rendering the next segment —
despite the block already being split at MIDI event boundaries specifically for
sample-accurate note-on/note-off. A pitch-bend or mod-wheel message landing mid-block
would silently wait until the *next* `processBlock()` call to take effect, even though the
existing segment-splitting machinery implies per-message accuracy was intended.

**Fixed** ([PluginProcessor.cpp:699-731](../Source/PluginProcessor.cpp)): factored the
push into a local `applyPerformanceState()` lambda, called once before the first segment
and again after every `handleMidiMessage()` call, so a pitch-bend/mod-wheel change now
takes effect at its correct sample position within the block, matching note-on/off's
existing accuracy. Verified: rebuilds clean, sanity render still NaN/Inf/clip-free.

## #19 — Non-LTI feedback loops (pitch shifters), empirical decay-slope test

**N/A by architecture, verified empirically anyway per the audit brief's instruction not
to reason about it abstractly.**

Traced the signal flow: `AiryChoirLayer::renderVoice` sums each voice's swept/enveloped
signal into `shimmerBus` ([AiryChoirLayer.cpp:128-129](../Source/dsp/AiryChoirLayer.cpp));
`renderLayerTail` runs that bus through highpass → `OctaveShimmer` → `shimmerReverb` once,
then adds it straight into the stereo output at a fixed 0.16 gain
([AiryChoirLayer.cpp:133-158](../Source/dsp/AiryChoirLayer.cpp)). Nothing routes that
output back into `shimmerBus` — it's a single-pass parallel send (matching
`FxChain.h`'s own doc comment describing it as a "parallel shimmer send"), not the
shimmer-inside-a-reverb-feedback-loop topology the playbook's Part 8.4/13 examples assume.
There is also no user-facing "shimmer feedback amount" parameter at all — the pitch ratio
is a fixed `2.0` (+1 octave) and `shimmerReverb`'s `roomSize`/`damping` are hardcoded, not
tied to any macro.

Ran the Part 8.4 measurement anyway, adapted for a synth (no raw audio input to inject a
literal click — used the layer's own attack transient with `attack=0`/`release=0` macros
for a near-click-like impulse instead) against `--solo=expanse`, 60s tail, octave-band
`scipy` Butterworth filter + linear dB-vs-time fit:

1. **Single-note click-equivalent**, own reverb only (`reverb=0` to isolate from the
   shared `FxChain` reverb): every measurable band decayed, fastest slopes around
   -51 to -65 dB/s (well past the -3dB/s bar), several bands dropped below the noise floor
   too fast to even fit a slope (i.e., decayed faster than measurable).
2. **Sustained 3-note chord** (program-dependence check, normal attack/release, own reverb
   only): same pattern, measurable band at -61 dB/s.
3. **Single-note click-equivalent combined with the shared `FxChain` reverb at REVERB=100%**
   (worst-case combined path): every one of 8 measurable bands (63Hz-8kHz) decayed, from
   -27 to -144 dB/s, none flat or growing.

No band in any of the three tests showed a zero or positive slope. No NaN/Inf/clipping in
any render (`safety.hasNanOrInf: false`, `safety.trueClipping: false` throughout).

## Fixes applied

### 1. `Source/dsp/FxChain.h` — restored `kWetCalibrationGain`, corrected its doc comment

**Before this audit** (already on disk, uncommitted, not made by this audit):
`kWetCalibrationGain = 0.48f`, comment claiming a "~2x RMS energy" calibration measured
"fixed note, dry vs. fully-wet RMS at REVERB=1".

**During this audit** (now reverted): temporarily set to `0.2f`, based on a since-proven-
unreliable single/triple-sample full-mix measurement that showed REVERB climbing the
output by +7.6dB. That measurement was a false alarm caused by run-to-run RMS variance
from multi-oscillator beat interference in the un-solo'd full mix (see #8 above).

**After this audit**: reverted to `kWetCalibrationGain = 0.48f` (the original, correct
value) with an expanded doc comment recording the 2026-09-20 re-verification numbers and
warning future readers not to re-tune this constant from a low-N full-mix sweep. Verified
flat (within ~0.5-1.2dB, i.e. within run-to-run noise) on both a solo'd single layer and
the full 4-layer default mix, N=5 renders per point — see #8 for the numbers.

### 2. `Source/PluginProcessor.cpp` — pitch-bend/mod-wheel mid-block staleness

See #18 above for the full description. Before: `layer->setPerformance()` called once per
`processBlock`, before the MIDI loop. After: factored into `applyPerformanceState()`,
called once before the first segment and again after every MIDI message, so mid-block
pitch-bend/mod-wheel changes take effect at their correct sample position instead of being
deferred to the next block.
